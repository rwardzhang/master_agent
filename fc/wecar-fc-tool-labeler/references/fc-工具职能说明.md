# 车机 Agent 工具详细边界说明

本文是 `wecar-fc-tool-labeler` 的**主参考文档**。

目标不是只告诉“这个工具大概能做什么”，而是要把**边界**讲清楚：
- 什么 query 应该落这个工具
- 什么 query 看起来像，但**绝不能**落这个工具
- 与同域其它工具怎么切分
- 在什么前提下才能用
- 应该输出什么标准 `assistant` 字符串

## 一、全局判断规则

### 1. 输出格式

所有 `assistant` 一律输出：

```text
工具名|参数1|参数2|...
```

通用要求：
- 没有值时统一填 `-`
- 不能缺参数位，也不能多参数位
- 序号从 `1` 开始
- 布尔/枚举必须写固定字面量，如 `true` / `false`、`driving` / `future`
- 多个途经点统一用 `;` 分隔
- `unknown` 的固定写法就是 `unknown|-`

### 2. `unknown` 不是“不确定”出口

`unknown` 只在三种情况下用：
1. **能力缺失**：当前域工具集根本做不到
2. **跨域越界**：这事属于别的域，但当前域不能代劳
3. **前置缺失**：本来有工具，但缺必要上下文，例如没有列表却说“第二个”

### 3. 强依赖上文列表的工具

以下工具一般都要求上一轮已经给出**本域列表**，否则不能硬标：
- `load_more`
- `poi_detail`
- `music_detail`
- `play_music`（按序号时）
- `movie_detail`
- `news_detail`
- `open_news`

### 4. 序号类 query 的统一判断

当用户说“第几个 / 第几首 / 最后一个”时，先判断上文有没有**本域列表**：
- 有列表 + 用户要执行动作 → 执行类工具
- 有列表 + 用户要问信息 → 详情类工具
- 没列表 → `unknown`

### 5. 所有域共同排除的请求

以下请求基本都不应落入这 27 个工具中的正常业务工具：
- 车控：空调、车窗、天窗、后备箱、灯光、座椅、媒体音量、投屏
- 日程：提醒、闹钟、待办、行程新增
- 通讯：打电话给某人、发微信、发短信
- 助手身份：你是谁、你叫什么、陪我聊天
- 内容创作：写诗、写文章、写代码、讲笑话
- 纯寒暄：你好、谢谢、再见

### 6. POI 参数抽取总原则（重点）

这部分优先级很高，尤其影响 `navigation`、`plan_route`、`search_along_route`、`search_place`、`poi_detail`。

- **先定角色，再抽参数**：先判断某个地点在句子里扮演的是“终点 / 起点 / 途经点 / 搜索目标 / 搜索中心点 / 详情对象”，不要一看到地名就机械塞到第一个参数。
- **纯地点名默认是目标，不是中心点**：用户只说“搜深圳湾公园”“去深圳北站”“导航到腾讯大厦”，地点名默认是目标对象，不能误填到 `near_address` 或 `origin`。
- **带“附近/周边/旁边/这附近”的地点才可能拆成中心点**：如“腾讯大厦附近的咖啡店”要拆成 `search_query=咖啡店`、`near_address=腾讯大厦`；没有这类中心约束时，不要硬拆。
- **当前位置是隐式参数，不是每次都要写出来**：
  - `plan_route` / `navigation` / `search_along_route` 里，用户默认从当前位置出发时，起点通常写 `-`
  - `search_place` 里，用户明确说“附近 / 我周围 / 这附近”时，`near_address` 可以写 `当前位置`
- **上下文可补全，但只能补“当前轮唯一能确定的对象”**：
  - 上一轮刚搜过地点列表，用户说“去第一家”/“第二个怎么走”/“这家店电话是多少”，可以从上文列表承接对象
  - 上一轮刚在出行域确定终点，用户说“路上找个充电站”，可以继承当前路线终点
  - 若上文对象不唯一，或跨域跳转后引用已经失焦，不要强行补全
- **补槽式短回复要继承上一轮意图**：如果上一轮 assistant 正在追问缺失槽位，如“杭州还是苏州”“什么时候出发”“第几个”，当前轮只回复“苏州吧 / 五一 / 第一个吧”时，不要把它当成新的独立 query；应回到上一轮待完成的工具或规划意图继续补齐参数
- **消歧后先看“新确认的槽位”是否正确**：当前轮若只是补最终目的地、选中候选项或回答澄清问题，先判断这轮新增确认的 `destination / index / city` 等槽位是否选对
- **已锁定旧参数是否必须重写，要区分“自包含标注”与“运行态补槽”**：
  - 若任务要求每条 `assistant` 都是完整可执行串，则上一轮已经确定的 `waypoints`、`near_address`、既有筛选条件等应回填，不能丢
  - 若是线上日志审计或运行态补槽场景，这一轮只是确认候选目的地，旧参数可能由系统状态保留；此时**不要仅因未重写旧参数就把 case 直接判成目标错误**
  - 例如“导航到万达广场，途经同庆楼(银湖店)”后接“到高铁站近的那个”，`destination=芜湖镜湖万达广场` 选对本身就应先判为正确；`waypoints` 是否再写出，要看当前数据口径是否要求自包含
- **指代词要先解引用**：`这儿/这里/这附近` 通常指当前位置；`那里/那边/那家/那个地方` 通常指上文最近一次明确提到的 POI；`回家/回公司` 属于记忆槽位目的地，不是普通文本问答
- **多地点句要识别主次关系**：
  - `先去A，再去B`：A 是途经点，B 是最终目的地
  - `从A到B`：A 是起点，B 是终点
  - `A附近找B`：A 是中心点，B 是搜索目标
  - `去B路上找A`：A 是沿途搜索关键词，B 是终点
- **能归一就归一**：兴趣点类型尽量归一为稳定写法，如“冲个电/充电的地方/补电站”统一成“充电站”；明显 ASR 噪声不要原样塞进参数
- **不要把动作词带进参数**：参数里尽量只保留 POI 本体或检索目标，不保留“导航去 / 搜一下 / 带我去 / 帮我找 / 看看有没有”这类壳子
- **不要把整个原句塞成一个参数**：除 `travel_plan|query` 外，大多数工具都要做槽位拆分。比如“腾讯大厦附近找咖啡店”不能写成 `search_place|腾讯大厦附近找咖啡店|-`

## 二、出行域

### 1. `navigation`
- **参数格式**：`navigation|destination|waypoints`
- **核心职责**：发起导航，让系统“现在就带我去某地”
- **典型意图**：去某地、带我去、导航去、回家、回公司、先去 A 再去 B
- **必要前提**：目的地必须明确；若有多个途经点，应把最终目的地放在 `destination`，中间点放 `waypoints`
- **绝不能标成它的情况**：
  - 用户只是在问“多远 / 多久 / 怎么走” → 应是 `plan_route`
  - 用户是在问“路上找个充电站” → 应是 `search_along_route`
  - 用户是在做“几日游 / 周末行程 / 攻略” → 应是 `travel_plan`
- **详细边界**：
  - **vs `plan_route`**：`navigation` 是“执行”，`plan_route` 是“查信息”
  - **vs `search_along_route`**：`navigation` 的主目标是到达终点，`search_along_route` 是在已知路线中途加搜点
  - **vs `travel_plan`**：`navigation` 是单次出发动作，`travel_plan` 是内容策划
  - **记忆槽位边界**：`导航回家` 可以是 `navigation|家|-`；但 `我家地址是什么` 不能用 `navigation`
- **参数提取规则（重点）**：
  - `destination` 取“最终要到达的那个 POI”，不是第一个出现的地名
  - 句式 `先去A，再去B，最后去C`：`destination=C`，`waypoints=A;B`
  - 句式 `去公司前先去星巴克`：最终目标是“公司”，不是“星巴克” → `navigation|公司|星巴克`
  - 用户说“回家 / 回公司 / 去单位”时，不要改写成问句或塞进 `waypoints`；`destination` 取值按【用户记忆】判定（2026.08.27 训练集实证）：记忆中有家/公司地址时**优先展开为记忆中的地址**（主流做法，65%，如 `navigation|深圳南山区蛇口花园城|-`）；记忆无对应地址时才保留槽位名 `家 / 公司`（35%）。`plan_route` 的家/公司槽位同理且更严格：记忆有地址时一律展开（9/9 先例，如「从家到公司」+记忆 → `plan_route|北京市朝阳区建国路88号|北京市海淀区中关村软件园|driving|-`）
  - 上一轮若已经明确唯一 POI，用户说“去那儿 / 就去这里 / 导航到这家店”，可以把该 POI 解析到 `destination`
  - **多轮候选消歧时，当前轮只要把目的地选对，就先判 `destination` 正确**：例如先给出多个“万达广场”候选，用户再说“到高铁站近的那个”，这轮核心是从候选里选中正确 `destination`
  - **`waypoints` 是否必须在消歧轮重写，要看数据口径**：
    - 若要求每条输出自包含，推荐回填旧的 `waypoints`
    - 若是运行态补槽或线上日志审计，系统可能保留上一轮已锁定的 `waypoints`；这时像 `navigation|芜湖镜湖万达广场|-` 这种“只更新 destination”的写法也可接受
  - “从当前位置出发”是默认前提，不需要额外编码到参数；`navigation` 没有起点参数
  - 不要把动作词带入参数：写 `深圳北站`，不要写 `去深圳北站` / `导航去深圳北站`

**标准示例**
```text
query: 带我去深圳北站
output: navigation|深圳北站|-
```
```text
query: 导航回家
output: navigation|家|-
```
```text
query: 先去加油站，再去南山书城
output: navigation|南山书城|加油站
```
```text
query: 去公司前先去一趟星巴克
output: navigation|公司|星巴克
```
```text
query: 上一轮已经找到“海岸城店”，这轮说：就去这家
output: navigation|海岸城店|-
```
```text
query: 上一轮说“导航到万达广场，途经同庆楼(银湖店)”，assistant 给出多个候选；这轮说：到高铁站近的那个
output: navigation|芜湖镜湖万达广场|-
```
- 说明：如果你的数据口径要求每条 `assistant` 自包含，也可以写成 `navigation|芜湖镜湖万达广场|同庆楼(银湖店)`；但在日志审计场景下，不应仅因未重写旧 `waypoints` 就把前者直接判错。

**易错反例**
```text
query: 从家到深圳北站开车要多久
wrong: navigation|深圳北站|-
right: plan_route|家|深圳北站|driving|-
```
```text
query: 深圳北站附近找个咖啡店
wrong: navigation|深圳北站|咖啡店
right: search_place|咖啡店|深圳北站
```

### 2. `plan_route`
- **参数格式**：`plan_route|origin|destination|travel_mode|waypoints`
- **核心职责**：查询路线信息，而不是发起导航
- **典型意图**：怎么走、多远、多久、堵不堵、哪条路线快、坐地铁怎么去、步行多久
- **必要前提**：终点必须明确；起点如果是当前位置可填 `-`
- **绝不能标成它的情况**：
  - “直接去某地” → `navigation`
  - “去深圳北站路上找充电站” → `search_along_route`
  - “帮我做两日游行程” → `travel_plan`
- **详细边界**：
  - 含“地铁 / 公交 / 骑行 / 步行 / 打车”等交通方式，优先判断为 `plan_route`
  - 含“路线 / 怎么走 / 几公里 / 多远 / 多久 / 要多长时间”，通常都是 `plan_route`
  - 即便出现“去某地”，只要用户在问路况信息而不是发起动作，也要落 `plan_route`
- **参数提取规则（重点）**：
  - `origin` 抽“从哪出发”。有显式 `从A / 由A / 离A` 就填 A；显式说“从当前位置 / 从这儿出发”时填【当前位置】的完整地址（2026.08.27 训练集 12/12 先例，如 `plan_route|广东省深圳市南山区腾讯滨海大厦(海天二路南)|深圳湾公园|driving|-`）；完全没提起点时才填 `-`
  - `destination` 抽“到哪去”。`到B / 去B / 回家 / 回公司 / 到那里` 里的 B 或被指代对象填这里
  - `travel_mode` 只看交通方式，不看是否真实执行：
    - 开车/驾车/打车/自驾/堵不堵/几公里 → `driving`
    - 公交/地铁/换乘 → `transit`
    - 步行/走路 → `walking`
    - 骑行/骑车 → `bicycling`
    - 电动车/电瓶车 → `ebicycling`
  - 上下文有唯一 POI 时，`这儿到机场多久` 可解析为 `origin=当前位置` 对应 `-`，`destination=机场`
  - 上下文刚给过候选地点，用户问“从第一家到公司多久”，可以把“第一家”承接成起点 POI
  - **多站点路线是 `plan_route` 的允许形态**：像“从A出发，先去B，再去C 的驾车路线”这种问法，工具仍然选 `plan_route`
  - **`waypoints` 抽途经点（按 2026.08.27 训练集实证对齐，1343/1358=98.9% 填 `-`）**：「先去B，再去C」「经B到C」句式的中间站 B **不入** `waypoints`——B 只用于确定 `destination=C`，`waypoints` 填 `-`（同场景先例：「先前往长安亭院火锅，再前往璟德·茶馆」→ `waypoints=-`）；仅显式「途经 / 路过 X」且 X 为城市级 / 服务区级地名（如“途经东莞”“路过阳澄湖服务区”）才填值，多个用 `;` 分隔。注意与 `navigation` 不同：`navigation` 的「先去A再去B」中间站**要**填 `waypoints`（训练集 214 条先例）
  - 不要把“多远 / 多久 / 怎么走”这类问法塞进参数，只保留起终点与方式

**标准示例**
```text
query: 从家到深圳北站开车要多久
output: plan_route|家|深圳北站|driving|-
（无记忆时保留槽位名；【用户记忆】有家地址时展开，如 plan_route|深圳南山区蛇口花园城|深圳北站|driving|-）
```
```text
query: 坐地铁去福田口岸怎么走
output: plan_route|-|福田口岸|transit|-
```
```text
query: 步行去腾讯大厦远吗
output: plan_route|-|腾讯大厦|walking|-
```
```text
query: 从公司到宝安机场打车多久
output: plan_route|公司|宝安机场|driving|-
（无记忆时保留槽位名；有公司地址记忆时展开为记忆地址）
```
```text
query: 规划从腾讯滨海大厦出发，先去长安亭院火锅，再去璟德·茶馆的驾车路线
output: plan_route|腾讯滨海大厦|璟德·茶馆|driving|-
（训练集实证：中间站长安亭院火锅不入 waypoints，填 `-`；destination 取最后要去的璟德·茶馆）
```
```text
query: 上一轮已经定位在海岸城，这轮说：从这儿去深圳北站要多久
output: plan_route|-|深圳北站|driving|-
```

**易错反例**
```text
query: 导航去福田口岸
wrong: plan_route|-|福田口岸|driving|-
right: navigation|福田口岸|-
```
```text
query: 去深圳北站路上找个充电站
wrong: plan_route|-|深圳北站|driving|-
right: search_along_route|充电站|-|深圳北站|-
```

### 3. `search_along_route`
- **参数格式**：`search_along_route|keyword|origin|destination|waypoints`
- **核心职责**：在既有路线或明确终点的前提下，顺路搜索兴趣点
- **典型意图**：路上找加油站、顺路找充电站、沿途找服务区、去某地途中找药店
- **必要前提**：必须有明确路线语境，至少终点要清楚
- **绝不能标成它的情况**：
  - 只是当前位置附近搜点 → `search_place`
  - 直接要去目的地 → `navigation`
  - 先问到某地怎么走 → `plan_route`
- **详细边界**：
  - “路上 / 沿途 / 顺路”是最强信号
  - `keyword` 要写成兴趣点类型或名称，不要原样抄 ASR 噪声
  - 如果用户只说“找个充电站”，没说是在路上还是附近，通常不是 `search_along_route`
- **参数提取规则（重点）**：
  - `keyword` 抽的是“想顺路找什么”，通常是 POI 类别或店名，如“加油站 / 充电站 / 海底捞”
  - `destination` 抽的是当前路线终点：
    - 句内明确给出时直接取，如“去深圳北站路上找个充电站”
    - 句内没说，但上文已经明确在导航去某地时，可继承上文终点
  - `origin` 只有用户明确说“从A到B路上”时才填 A；默认从当前位置或当前路线起点出发时可填 `-`
  - `waypoints` 抽途经点，多个用 `;` 分隔；**按 2026.08.27 训练集实证（462/477=96.6%）绝大多数填 `-`**，仅显式「途经 / 路过」城市级 / 服务区级地名才填值（与 `plan_route` 同口径；途经点不能丢“地址范围修饰词”）
  - “顺路看看有没有加油站”这类句子，只有在上文已经存在明确路线时才应落 `search_along_route`；否则更可能是信息不足或普通附近搜索
  - `keyword` 需要归一化：如“冲个电 / 充电的地方 / 补能站”优先统一成“充电站”

**标准示例**
```text
query: 去深圳北站路上找个充电站
output: search_along_route|充电站|-|深圳北站|-
```
```text
query: 从公司去机场路上找个加油站
output: search_along_route|加油站|公司|机场|-
```
```text
query: 上一轮正在导航去深圳北站，这轮说：顺路看看有没有服务区
output: search_along_route|服务区|-|深圳北站|-
```

**易错反例**
```text
query: 腾讯滨海大厦附近有什么咖啡店
wrong: search_along_route|咖啡店|腾讯滨海大厦|-|-
right: search_place|咖啡店|腾讯滨海大厦
```
```text
query: 顺路看看有没有加油站（但上文没有任何路线）
wrong: search_along_route|加油站|-|-|-
right: unknown|-
```

### 4. `travel_plan`
- **参数格式**：`travel_plan|query`
- **核心职责**：生成行程/攻略/几日游方案，不是导航也不是路线计算
- **典型意图**：周末去哪玩、两日游怎么安排、自驾路线规划、旅行攻略、亲子游方案
- **必要前提**：应把用户的意图提炼为完整需求，不是机械复读原话
- **绝不能标成它的情况**：
  - “去某地怎么走” → `plan_route`
  - “导航去某地” → `navigation`
  - “去某地路上找个充电站” → `search_along_route`
- **详细边界**：
  - 只要问题核心是“玩什么、怎么安排”，就偏向 `travel_plan`
  - 可以补全城市、天数、主题、方式，但不能凭空增加用户没给出的强约束
  - query 一般应该是概括后的检索/规划语句，而不是原始口语

**标准示例**
```text
query: 周末去深圳周边玩两天，帮我规划一下
output: travel_plan|周末深圳周边两日游行程规划
```
```text
query: 帮我规划一条武汉赏樱自驾路线
output: travel_plan|武汉赏樱自驾路线规划
```

**易错反例**
```text
query: 坐地铁去福田口岸怎么走
wrong: travel_plan|去福田口岸路线规划
right: plan_route|-|福田口岸|transit|-
```

### 5. `call_telephone`
- **参数格式**：`call_telephone|phone|index`
- **核心职责**：拨打已经明确给出的电话号码
- **典型意图**：拨打某个号码、给出号码后让系统呼出
- **必要前提**：对话里已经有完整号码，或者列表序号能唯一落到电话对象
- **绝不能标成它的情况**：
  - “这家店电话是多少” → 这是问信息，不是拨号
  - “帮我给这家店打电话”但上下文没有号码 → 通常不能直接用 `call_telephone`
- **详细边界**：
  - 这是一个很窄的工具，只在“号码已知且明确要拨”时用
  - 绝大多数“电话”相关 query，在地点域里其实是 `poi_detail`

**标准示例**
```text
query: 拨打 075586001234
output: call_telephone|075586001234|-
```

### 6. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接本域做不到的请求
- **典型意图**：交停车费、查违章、查限行、查过路费、查航班晚点、反查家庭住址
- **绝不能标成它的情况**：本域已有工具能完成的 query 不能懒得扔给 `unknown`
- **详细边界**：
  - “我家地址是什么”是查槽位内容，不是导航动作 → `unknown`
  - “我的车今天限行吗”属于车务信息，不在出行域工具覆盖内 → `unknown`

**标准示例**
```text
query: 我的车今天限行吗
output: unknown|-
```
```text
query: 我家地址是什么
output: unknown|-
```

## 三、地点域

### 1. `search_place`
- **参数格式**：`search_place|search_query|near_address`
- **核心职责**：发起新的地点搜索
- **典型意图**：搜索某个地点、搜索某类店、在某地附近找餐馆/咖啡店/停车场
- **必要前提**：如果用户搜的是纯地点名，地点名应填在 `search_query`，不是 `near_address`
- **绝不能标成它的情况**：
  - 用户在问列表内某家店详情 → `poi_detail`
  - 用户只是想翻更多列表 → `load_more`
  - 用户要导航去 → 不是地点域
- **详细边界**：
  - “搜索深圳湾公园” → `search_query=深圳湾公园`，`near_address=-`
  - 只有“某地附近找 X”才把中心点写到 `near_address`
  - 搜索电影院是地点搜索；搜索电影内容不是地点搜索
- **参数提取规则（重点）**：
  - `search_query` 放“要找的东西”，即目标 POI 名称、POI 类别或品牌，如“深圳湾公园 / 咖啡店 / 海底捞 / 充电站”
  - `near_address` 放“围绕哪个中心搜”，只有存在明确中心约束时才填，如“腾讯大厦附近 / 南山书城周边 / 这附近 / 我周围”
  - **纯地点名不要拆**：
    - “搜深圳湾公园” → `search_place|深圳湾公园|-`
    - 不能写成 `search_place|-|深圳湾公园`
  - **只有“中心点 + 目标类目”结构才拆槽**：
    - “腾讯滨海大厦附近的咖啡店” → `search_query=咖啡店`，`near_address=腾讯滨海大厦`
    - “离深圳北站近的酒店” → `search_query=酒店`，`near_address=深圳北站`
  - **当前位置场景要显式识别**：
    - “附近有什么停车场 / 我周围的咖啡店 / 这附近有洗手间吗” → `near_address=当前位置`
    - 不要把“附近”塞进 `search_query`
  - **上下文承接**：
    - 上一轮已经确定中心点，当前轮只换目标，如“腾讯大厦附近有什么咖啡店”后接“换成便利店”，应继承中心点 → `search_place|便利店|腾讯大厦`
    - 上一轮刚在地点域说“搜海岸城附近餐厅”，下一轮说“再找停车场”，如果语义明显仍围绕同一中心点，可以继承 `near_address=海岸城`
  - **不要过度承接**：如果上一轮是出行/新闻/音乐等无关域，或可承接对象不唯一，不要擅自补 `near_address`
  - **品牌名+中心点都在时，品牌名仍然放 `search_query`**：如“腾讯大厦附近的海底捞” → `search_place|海底捞|腾讯大厦`
  - **问详情不是搜索**：如果用户已经锁定一个明确 POI 并询问电话、营业时间、评分，应该去 `poi_detail`，而不是 `search_place`

**标准示例**
```text
query: 搜索深圳湾公园
output: search_place|深圳湾公园|-
```
```text
query: 腾讯滨海大厦附近有什么咖啡店
output: search_place|咖啡店|腾讯滨海大厦
```
```text
query: 这附近有停车场吗
output: search_place|停车场|当前位置
```
```text
query: 上一轮是“腾讯大厦附近有什么咖啡店”，这轮说：换成便利店
output: search_place|便利店|腾讯大厦
```
```text
query: 帮我找离深圳北站近一点的酒店
output: search_place|酒店|深圳北站
```

**易错反例**
```text
query: 海底捞电话是多少
wrong: search_place|海底捞|-
right: poi_detail|-|海底捞
```
```text
query: 搜索深圳湾公园
wrong: search_place|-|深圳湾公园
right: search_place|深圳湾公园|-
```

### 2. `poi_detail`
- **参数格式**：`poi_detail|index|poi_name`
- **核心职责**：查询地点的标准属性信息
- **典型意图**：评分、人均、电话、营业时间、地址、停车场、特色菜、怎么样
- **必要前提**：按序号问时应有上文地点列表；直接点名地点时可用 `poi_name`
- **绝不能标成它的情况**：
  - 用户在要求拨打电话 → 不是 `poi_detail`
  - 用户在问 WiFi 密码/排队人数/收藏/分享 → 本工具不覆盖
- **详细边界**：
  - “电话是多少”是查详情，不是拨号
  - “第一个怎么样” / “第二家营业到几点”都是典型 `poi_detail`
  - 标准属性可以查，非标准属性通常不能查
- **参数提取规则（重点）**：
  - `index` 用于“第一个 / 第二家 / 最后一个 / 刚才那家（能唯一回指到列表项）”这类列表内指代
  - `poi_name` 用于用户直接说出明确 POI 名称，如“海底捞电话是多少”“深圳湾公园几点关门”
  - **优先级**：
    - 明确序号且上文有列表 → 优先填 `index`，`poi_name=-`
    - 没有序号，但有明确地点名 → 填 `poi_name`，`index=-`
    - 指代词“这家 / 那家 / 这个店”只有在上文存在唯一聚焦 POI 或列表项时才能补全
  - **上下文承接**：
    - 上一轮展示过地点列表，用户说“第二家电话是多少” → `poi_detail|2|-`
    - 上一轮只剩一个当前讨论对象，用户说“这家几点关门” → 可回填为对应 `index` 或 `poi_name`
    - 若上文给过多家店但没有唯一锚点，单说“这家店怎么样”不可强行猜测
  - **属性词不进参数**：电话、营业时间、评分、停车场等属于问法线索，不进入参数位；参数里只保留索引或 POI 本体
  - **当前位置不是 `poi_detail` 参数**：如“我附近这家店电话是多少”，真正要填的是被指向的店，而不是“当前位置”
  - **详情 vs 动作**：
    - “电话是多少” / “营业到几点” / “有停车场吗” → `poi_detail`
    - “帮我打电话给这家店” → 执行动作，不是 `poi_detail`

**标准示例**
```text
query: 第二家营业到几点
output: poi_detail|2|-
```
```text
query: 海底捞电话是多少
output: poi_detail|-|海底捞
```
```text
query: 第一家评分怎样
output: poi_detail|1|-
```
```text
query: 上一轮只在讨论“海岸城店”，这轮说：这家店停车方便吗
output: poi_detail|-|海岸城店
```
```text
query: 上一轮给了 3 家店的列表，这轮说：最后一家地址在哪
output: poi_detail|3|-
```

**易错反例**
```text
query: 帮我打电话给这家店
wrong: poi_detail|1|-
right: unknown|-
```
```text
query: 这附近有什么咖啡店
wrong: poi_detail|-|咖啡店
right: search_place|咖啡店|当前位置
```

### 3. `load_more`
- **参数格式**：`load_more|-`
- **核心职责**：地点列表翻页或继续展示更多结果
- **典型意图**：还有吗、再来几个、换一批、下一页
- **必要前提**：上文必须已有地点列表
- **绝不能标成它的情况**：没有列表上下文时的“换一批”
- **详细边界**：
  - `load_more` 不创造新搜索条件，只承接上一轮列表
  - 如果用户重新指定了条件，如“换成咖啡店”，就不是 `load_more`

**标准示例**
```text
query: 还有别的吗
output: load_more|-
```

### 4. `call_telephone`
- **参数格式**：`call_telephone|phone|index`
- **核心职责**：拨打已明确给出的号码
- **典型意图**：拨打这个电话、呼出此号码
- **必要前提**：号码已知，且用户明确要求拨打
- **绝不能标成它的情况**：问店铺电话；“给这家店打电话”但没有具体号码
- **详细边界**：
  - 地点域里“电话相关”多数不是拨号，而是 `poi_detail`
  - 只有极少数场景才用 `call_telephone`

**标准示例**
```text
query: 拨打 4008308300
output: call_telephone|4008308300|-
```

### 5. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接地点域没有工具处理的动作
- **典型意图**：订座、排队、分享地点、收藏地点、查 WiFi 密码、查路名、导航前往
- **绝不能标成它的情况**：地点搜索和标准属性查询
- **详细边界**：
  - “这家店的 WiFi 密码是多少”虽与地点有关，但不是标准可查属性
  - “帮我订一下这家餐厅的位置”虽与餐厅有关，但这是执行类能力缺失

**标准示例**
```text
query: 帮我订一下这家餐厅的位置
output: unknown|-
```
```text
query: 这家店的 WiFi 密码是多少
output: unknown|-
```

## 四、音乐域

### 1. `music_search`
- **参数格式**：`music_search|query|need_play|random_search`
- **核心职责**：搜索歌曲或歌曲集合
- **典型意图**：找某歌手的歌、按歌名搜、按歌词片段搜、按风格搜、来点音乐
- **必要前提**：
  - `query` 应是提炼后的搜索词，不要把“找一下 / 搜一下”原样保留
  - 只有 `query='-'` 且完全无指向时，`random_search=true`
- **绝不能标成它的情况**：
  - 上文有列表且用户说“放第2首” → `play_music`
  - 问某首歌创作背景 → `music_detail`
  - 问歌手代表作/获奖 → `web_search`
- **详细边界**：
  - “找一下周杰伦的歌” → `music_search|周杰伦的歌曲|false|false`
  - “来点音乐” → 随机搜索且通常直接播，`music_search|-|true|true`
  - 风格词如“轻松 / 治愈 / 安静”也算有指向，通常 `random_search=false`

**标准示例**
```text
query: 找一下周杰伦的歌
output: music_search|周杰伦的歌曲|false|false
```
```text
query: 来点音乐
output: music_search|-|true|true
```
```text
query: 播放轻松一点的歌
output: music_search|轻松一点的歌|true|false
```

### 2. `play_music`
- **参数格式**：`play_music|index|song_name`
- **核心职责**：播放已经明确的歌曲对象
- **典型意图**：播放某首歌、放第几首、来一首某歌
- **必要前提**：
  - 按序号播时，要有上文歌曲列表
  - 直接点歌名时可不用列表
- **绝不能标成它的情况**：
  - 用户还在搜索阶段 → `music_search`
  - 用户在问歌曲信息 → `music_detail`
  - 用户要求暂停/下一首/调音量 → `unknown`
- **详细边界**：
  - “放第2首” 是典型 `play_music`
  - “播放起风了” 目标已经明确，可直接 `play_music`
  - “找一首周杰伦的歌” 不应直接 `play_music`

**标准示例**
```text
query: 放第2首
output: play_music|2|-
```
```text
query: 播放起风了
output: play_music|-|起风了
```

### 3. `music_detail`
- **参数格式**：`music_detail|index|title`
- **核心职责**：查询单首歌曲的内容与背景
- **典型意图**：这首歌怎么样、谁写的、创作背景、讲的是什么
- **必要前提**：按序号问时要有列表；直接点歌名则不必有列表
- **绝不能标成它的情况**：
  - 用户问歌手代表作/获奖/榜单 → `web_search`
  - 用户要播放 → `play_music`
  - 用户只是搜索歌曲 → `music_search`
- **详细边界**：
  - `music_detail` 的对象是“单首歌”
  - `web_search` 的对象通常是“歌手 / 专辑 / 节目 / 榜单”层面的知识

**标准示例**
```text
query: 第三首歌怎么样
output: music_detail|3|-
```
```text
query: 富士山下的创作背景是什么
output: music_detail|-|富士山下
```

### 4. `web_search`
- **参数格式**：`web_search|-`
- **核心职责**：处理音乐领域的知识性问答
- **典型意图**：歌手代表作、获奖经历、春晚、榜单、专辑收录、节目资讯
- **必要前提**：问题核心是“知识问答”，不是搜歌或播歌
- **绝不能标成它的情况**：
  - 搜歌 → `music_search`
  - 播放歌曲 → `play_music`
  - 歌手年龄、私人信息 → `unknown`
- **详细边界**：
  - “刘德华有哪些代表作” → `web_search`
  - “周杰伦得过哪些音乐奖” → `web_search`
  - “周杰伦多大了” 虽然也像知识问答，但按训练规则应是 `unknown`

**标准示例**
```text
query: 刘德华有哪些代表作
output: web_search|-
```
```text
query: 周杰伦得过哪些音乐奖
output: web_search|-
```

### 5. `load_more`
- **参数格式**：`load_more|-`
- **核心职责**：歌曲列表翻页或继续展示更多结果
- **典型意图**：还有别的歌吗、再来几首、换一批
- **必要前提**：上文已有歌曲列表
- **绝不能标成它的情况**：没有列表时的“还有吗”

**标准示例**
```text
query: 还有别的歌吗
output: load_more|-
```

### 6. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接音乐域做不到的请求
- **典型意图**：暂停、下一首、音量、显示歌词、收藏、下载、查当前播放态、问歌手年龄
- **绝不能标成它的情况**：搜歌、播歌、歌曲详情、歌手作品知识
- **详细边界**：
  - 音乐域不处理播放器控制
  - 音乐域的 `web_search` 也不覆盖歌手年龄等个人生平

**标准示例**
```text
query: 把歌停了
output: unknown|-
```
```text
query: 周杰伦今年多大了
output: unknown|-
```

## 五、新闻域

### 1. `news_search`
- **参数格式**：`news_search|query|category|region`
- **核心职责**：按主题、分类、地区检索新闻
- **典型意图**：科技新闻、广东新闻、英伟达新闻、热点新闻
- **必要前提**：
  - 只按分类/地区浏览时，`query` 可以是 `-`
  - `region` 写省级/直辖市，不要写过细城市层级
- **绝不能标成它的情况**：
  - 早报/晚报 → `news_briefing`
  - 某条新闻讲了什么 → `news_detail`
  - 点开新闻 → `open_news`
- **详细边界**：
  - `news_search` 是“找新闻”，不是“读新闻”
  - 若用户只说“看看科技新闻”，`query=-`，`category=科技`

**标准示例**
```text
query: 看看广东的科技新闻
output: news_search|-|科技|广东
```
```text
query: 查一下英伟达的新闻
output: news_search|英伟达|要闻|-
```

### 2. `news_briefing`
- **参数格式**：`news_briefing|when`
- **核心职责**：播报早报、晚报或简报
- **典型意图**：来一份早报、晚报、新闻简报
- **必要前提**：问题是“成篇播报”，不是找具体主题
- **绝不能标成它的情况**：指定新闻主题搜索

**标准示例**
```text
query: 来一份今天的新闻早报
output: news_briefing|morning
```
```text
query: 播报一下今晚的新闻晚报
output: news_briefing|night
```
```text
query: 来一份新闻简报
output: news_briefing|auto
```

### 3. `news_detail`
- **参数格式**：`news_detail|index|title`
- **核心职责**：在对话内讲某条新闻的内容、摘要、详情
- **典型意图**：第一条讲了什么、详细说说、展开讲讲
- **必要前提**：通常需要上文新闻列表
- **绝不能标成它的情况**：用户明确说“点开 / 打开 / 进入” → 应是 `open_news`
- **详细边界**：
  - “详情 / 讲了什么 / 详细讲讲” → `news_detail`
  - “点开 / 进入 / 打开” → `open_news`

**标准示例**
```text
query: 第一条讲了什么
output: news_detail|1|-
```
```text
query: 给我详细讲讲这条新闻
output: news_detail|1|-
```

### 4. `open_news`
- **参数格式**：`open_news|index|title`
- **核心职责**：打开新闻详情页
- **典型意图**：点开第二条、打开这条、进入详情页
- **必要前提**：通常要有上文新闻列表或明确指代对象
- **绝不能标成它的情况**：只是想听摘要或内容

**标准示例**
```text
query: 点开第二条
output: open_news|2|-
```
```text
query: 打开这条新闻
output: open_news|1|-
```

### 5. `load_more`
- **参数格式**：`load_more|-`
- **核心职责**：新闻列表翻页或更多结果
- **典型意图**：再来几条、还有吗、下一页
- **必要前提**：上文有新闻列表
- **绝不能标成它的情况**：没有列表上下文

**标准示例**
```text
query: 再来几条
output: load_more|-
```

### 6. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接新闻域不能处理的请求
- **典型意图**：查天气、找餐厅、发消息等跨域需求
- **绝不能标成它的情况**：新闻检索、简报、详情、打开页面

**标准示例**
```text
query: 帮我查一下今天深圳天气
output: unknown|-
```

## 六、语音设置域（speech）

### 1. `set`
- **参数格式**：`set|lang|emo|sty|role|speed|volume`
- **核心职责**：调整 AI 朗读声音参数
- **典型意图**：改语种、改情绪、改风格、改音色、讲快点/慢点、播报音量大一点
- **必要前提**：六个参数位固定顺序，只填变化位，其余填 `-`
- **绝不能标成它的情况**：
  - 恢复默认 → `reset_speech`
  - 调媒体音量/空调 → `unknown`
- **详细边界**：
  - 这个工具只管“AI 朗读声音”，不管车机系统声音
  - 调角色音色时，`role` 应用规则内的编号或合法字面量，不是随便写描述词

**标准示例**
```text
query: 用粤语温柔一点说
output: set|粤语|-|温柔|-|-|-
```
```text
query: 讲慢一点
output: set|-|-|-|-|-1|-
```
```text
query: 声音调大一点
output: set|-|-|-|-|-|1
```

### 2. `reset_speech`
- **参数格式**：`reset_speech|-`
- **核心职责**：把所有语音参数恢复默认
- **典型意图**：恢复默认、还是用回原来的、全部重置
- **必要前提**：用户意图是“回到默认状态”，不是局部调整
- **绝不能标成它的情况**：只改语速/语种/风格等单项设置

**标准示例**
```text
query: 恢复默认声音
output: reset_speech|-
```
```text
query: 还是用回原来的吧
output: reset_speech|-
```

### 3. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接非语音设置请求
- **典型意图**：调空调、调媒体音量、闲聊、问身份
- **绝不能标成它的情况**：任何语种/风格/角色/语速/音量参数设置

**标准示例**
```text
query: 把空调调低一点
output: unknown|-
```
```text
query: 把音乐声音调大一点
output: unknown|-
```

## 七、信息查询域

### 1. `weather`
- **参数格式**：`weather|address|weather_type`
- **核心职责**：天气查询
- **典型意图**：今天天气、明天天气、未来几天、未来几小时、会不会下雨
- **必要前提**：
  - `address` 只写市/区级，不写楼宇地标
  - `weather_type` 要和时间粒度匹配：`now` / `future` / `hours`
- **绝不能标成它的情况**：
  - 百科常识问答 → `web_search`
  - “现在几点” → `unknown`
- **详细边界**：
  - 今天/现在 → 多数是 `now`
  - 明天/未来几天/一周 → `future`
  - 未来几小时/逐小时/几点会下雨 → `hours`

**标准示例**
```text
query: 深圳南山区明天天气怎么样
output: weather|深圳南山区|future
```
```text
query: 深圳未来12小时会下雨吗
output: weather|深圳|hours
```
```text
query: 重庆今天天气怎么样
output: weather|重庆|now
```

### 2. `web_search`
- **参数格式**：`web_search|-`
- **核心职责**：通用知识/时效信息的联网搜索
- **典型意图**：星期几、几号、百科问答、节气、世界常识、百科解释
- **必要前提**：问题核心是信息查询而非天气、车控、提醒
- **绝不能标成它的情况**：
  - 天气 → `weather`
  - 现在几点 → `unknown`
  - 空调/提醒/闲聊 → `unknown`
- **详细边界**：
  - “今天星期几” 是 `web_search`
  - “珠穆朗玛峰有多高” 是 `web_search`
  - “现在几点” 不要误用 `web_search`

**标准示例**
```text
query: 今天星期几
output: web_search|-
```
```text
query: 珠穆朗玛峰有多高
output: web_search|-
```
```text
query: 咖啡因能提神多久
output: web_search|-
```

### 3. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接信息查询域做不到的请求
- **典型意图**：现在几点、设置提醒、开空调、闲聊、写文章
- **绝不能标成它的情况**：天气、百科搜索
- **详细边界**：
  - “现在几点” 是本域高频误判点，必须是 `unknown`
  - “今天星期几” 不一样，它是 `web_search`

**标准示例**
```text
query: 现在几点了
output: unknown|-
```
```text
query: 提醒我晚上八点开会
output: unknown|-
```

## 八、影院电影域

### 1. `movie_list`
- **参数格式**：`movie_list|kind|city|movie_name`
- **核心职责**：列出当前热映或即将上映片单，也承接“给我找个电影看看”这类**无明确偏好约束**的泛化选片请求
- **典型意图**：现在有什么电影、正在热映什么、即将上映什么、推荐个电影看看、找个电影随便看看
- **必要前提**：用户要的是“给我一些当前可看的电影候选”，而不是围绕题材/口味/人群做个性化推荐
- **绝不能标成它的情况**：
  - “推荐一部高分科幻电影” / “适合情侣看的电影” / “别太吓人的电影” → 这类带明显偏好约束的推荐超出当前片单 schema，归 `web_search`
  - “这部电影讲什么” → 详情或知识问答，不是列表
  - “明天几点开场” → `unknown`
- **详细边界**：
  - `movie_list` 的本质是“给候选片单”。因此除了显式片单问法，像“推荐个电影看看”“给我找个电影看”这种**未给筛选条件**的宽泛请求，也允许折算成当前城市热映片单，默认 `kind=hot`
  - 是否出现“推荐”二字不是唯一判断标准，关键看用户是不是在要**当前可看的候选列表**；若只是泛泛想看电影，没有题材、评分、人群、情绪等约束，`movie_list|hot|城市|-` 是合法压缩表达
  - `city` 优先取 query 中显式城市；没有显式城市时，可用当前位置归一到城市级，如“广东省深圳市南山区腾讯滨海大厦(白石路东)”归一为 `深圳`
  - `movie_name` 在用户明确指定某部电影名时填（如“查找《功夫女足》”→ 填 `功夫女足`；问“《长安三万里》什么时候上映”时对应 `kind=coming` 并填 `长安三万里`）；用户只是泛泛要片单、没点名具体影片时填 `-`
  - 若用户提出“高分/科幻/喜剧/适合小孩/适合约会/别太长/别太烧脑”等筛选诉求，当前 `movie_list` 无法表达这些约束，不能硬塞成 `movie_list`

**标准示例**
```text
query: 深圳现在有什么热映电影
output: movie_list|hot|深圳|-
```
```text
query: 北京即将上映哪些电影
output: movie_list|coming|北京|-
```
```text
query: 推荐个电影看看
output: movie_list|hot|深圳|-
```
```text
query: 查找《功夫女足》
output: movie_list|hot|深圳|功夫女足
```
```text
query: 《长安三万里》什么时候上映
output: movie_list|coming|广州|长安三万里
```

### 2. `movie_detail`
- **参数格式**：`movie_detail|index|movie_name`
- **核心职责**：查询电影详情
- **典型意图**：这部电影讲什么、评分多少、谁演的、上映时间、好不好看
- **必要前提**：通常需要列表上下文；直接点名影片时也可用 `movie_name`
- **绝不能标成它的情况**：
  - 用户问的是列表外作品百科知识且不依赖当前影院列表 → `web_search`
  - 用户问场次、票价、购票 → `unknown`
- **详细边界**：
  - “第一部讲什么” 明显是 `movie_detail`
  - “流浪地球 2 评分多少” 若按当前技能定义也可视作电影详情

**标准示例**
```text
query: 第一部讲什么
output: movie_detail|1|-
```
```text
query: 流浪地球 2 评分多少
output: movie_detail|-|流浪地球 2
```

### 3. `web_search`
- **参数格式**：`web_search|-`
- **核心职责**：处理已知影视作品/艺人的知识问答
- **典型意图**：剧情解析、为什么火、经典台词、更新到多少集、艺人籍贯
- **必要前提**：核心是“知识问答”，不是片单、购票、推荐、最新动态
- **绝不能标成它的情况**：
  - 带偏好约束的影片推荐（如高分/科幻/适合情侣）→ `unknown`
  - 场次票价购票 → `unknown`
  - 某人的最新作品 → `unknown`
  - **影人作品集列举**（XX有什么作品 / 代表作 / 演过哪些电影 / 导演过什么）→ `unknown`（2026.08.27 训练集 15 条先例一致，含刘德华/徐峥/诺兰/张艺谋/马丽等；注意与音乐域相反——歌手代表作 → `web_search`，**同一个人按所在域取不同标签**）
  - 在哪能看 / 在线观看 → `unknown`
- **详细边界**：
  - `web_search` 在影院域不等于“什么都能搜”
  - 只覆盖“已知对象的既有信息”，不覆盖实时动态和消费动作

**标准示例**
```text
query: 雷佳音是哪里人
output: web_search|-
```
```text
query: 狂飙为什么这么火
output: web_search|-
```
```text
query: 进击的巨人更新到多少集了
output: web_search|-
```

### 4. `load_more`
- **参数格式**：`load_more|-`
- **核心职责**：影片列表翻页或继续展示更多结果
- **典型意图**：再看看别的、换一批、下一页
- **必要前提**：上文已有影片列表
- **绝不能标成它的情况**：没有列表上下文

**标准示例**
```text
query: 再看看别的
output: load_more|-
```

### 5. `unknown`
- **参数格式**：`unknown|-`
- **核心职责**：承接影院域做不到的请求
- **典型意图**：带复杂偏好的影片推荐、查场次、查票价、买票、在线看、查票房、查最近影院、查最新作品、影人作品集列举
- **绝不能标成它的情况**：片单、泛化找片（如“推荐个电影看看”）、电影详情、已知作品知识问答
- **详细边界**：
  - “帮我推荐一部高分科幻电影” 是**带偏好约束**的推荐，当前 schema 不能表达 → `unknown`
  - “推荐个电影看看” 如果没有额外约束，应按当前城市热映片单处理，不应再打 `unknown`
  - “明天这部电影几点开场” 是场次 → `unknown`
  - “哪里能看甄嬛传” 是播放能力 → `unknown`
  - “某人最新作品是什么” 是实时动态 → `unknown`
  - **“刘德华有什么作品 / 徐峥导演过哪些电影 / 周迅演过哪些经典电影” 是影人作品集列举 → `unknown`**（训练集 15 条先例一致）。区别于**单部已知作品**的知识问答——“狂飙为什么火 / 进击的巨人更新到多少集” → `web_search`。判定要点：问的是“某人的作品列表”（unknown），还是“某部作品的具体信息”（web_search）

**标准示例**
```text
query: 帮我推荐一部高分科幻电影
output: unknown|-
```
```text
query: 刘德华有什么作品
output: unknown|-
```
```text
query: 徐峥导演过哪些电影
output: unknown|-
```text
query: 明天这部电影几点开场
output: unknown|-
```
```text
query: 这部电影票房多少
output: unknown|-
```

## 九、快速对照：最容易混的边界

### 1. 出行域
- `navigation`：去某地、立即导航
- `plan_route`：怎么走、多远、多久、路线对比
- `search_along_route`：去某地路上顺路找点
- `travel_plan`：行程/攻略/几日游

### 2. 地点域
- `search_place`：发起新地点搜索
- `poi_detail`：查列表内或已知地点的标准信息
- `call_telephone`：号码已明确且明确拨打
- `load_more`：上一轮列表翻页

### 3. 音乐域
- `music_search`：搜歌/搜歌集合
- `play_music`：播明确歌曲
- `music_detail`：单首歌的信息
- `web_search`：歌手/榜单/专辑知识问答
- 播放器控制一律不是这几个工具，通常 `unknown`

### 4. 新闻域
- `news_search`：找新闻
- `news_briefing`：早报/晚报/简报
- `news_detail`：在对话里讲内容
- `open_news`：打开页面

### 5. 信息查询域
- `weather`：天气
- `web_search`：百科/常识/日期/星期几
- `unknown`：现在几点、提醒、车控、闲聊

### 6. 影院域
- `movie_list`：当前档期片单
- `movie_detail`：电影详情
- `web_search`：已知影视作品/艺人的知识问答
- 推荐/购票/场次/在线看/票房/最新作品 → `unknown`
